# Market Changes Engine — Database Schema


## 1. Purpose


This document defines the initial PostgreSQL schema for Market Changes Engine.


Goals:


- preserve source lineage;

- retain historical state;

- support deterministic change detection;

- avoid provider-specific data leaking into application logic;

- keep the MVP simple enough for a modular monolith;

- make collectors idempotent;

- keep AI-generated content separate from objective market data.


---


## 2. Conventions


### Primary keys


Use:


```text

BIGINT GENERATED BY DEFAULT AS IDENTITY

```


or SQLAlchemy equivalent.


UUIDs are not required for the MVP unless external/public identifiers are later needed.


### Timestamps


Use:


```text

TIMESTAMPTZ

```


All application timestamps are UTC.


### Dates


Market-native dates such as trading dates use:


```text

DATE

```


### Money / financial values


Prefer:


```text

NUMERIC

```


for persisted financial values where exact decimal representation matters.


Use `DOUBLE PRECISION` only for derived statistical quantities where exact decimals are not required.


### JSON


Use:


```text

JSONB

```


for raw provider payloads and flexible metadata.


### Naming


Tables and columns use:


```text

snake_case

```

# 4. Core Reference Tables


## 4.1 `instruments`


Represents a tradable security tracked by the engine.


```sql

CREATE TABLE instruments (

    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,


    symbol              VARCHAR(32) NOT NULL,

    market              VARCHAR(16) NOT NULL,

    exchange            VARCHAR(32),

    company_name        VARCHAR(255) NOT NULL,


    currency            VARCHAR(8) NOT NULL,

    instrument_type     VARCHAR(32) NOT NULL DEFAULT 'equity',


    isin                VARCHAR(32),

    cusip               VARCHAR(32),

    sedol               VARCHAR(32),


    country_code        VARCHAR(8),

    timezone            VARCHAR(64),


    is_active           BOOLEAN NOT NULL DEFAULT TRUE,


    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),

    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now(),


    UNIQUE (market, symbol)

);

```


### Example


```text

symbol: AMD

market: US

exchange: NASDAQ

currency: USD

```


```text

symbol: 2330

market: TW

exchange: TWSE

currency: TWD

```


### Indexes


```sql

CREATE INDEX idx_instruments_symbol

ON instruments (symbol);


CREATE INDEX idx_instruments_market_active

ON instruments (market, is_active);

```

### Important design note


`previous_snapshot_id` and `current_snapshot_id` are intentionally paired with a snapshot type rather than hard foreign keys.


Reason:


`changes` may reference different snapshot tables.


MVP should enforce this relationship in application logic.


If stronger relational enforcement becomes necessary later, introduce a unified `observations` registry table.

# 12. Data Lineage


A normalized record should ideally follow:


```text

data_sources

      ↓

raw_ingestions

      ↓

normalized snapshot

      ↓

changes

      ↓

ai_interpretations

```


Example:


```text

Alpha Vantage

    ↓

raw_ingestions.id = 9001

    ↓

estimate_snapshots.id = 420

    ↓

changes.id = 101

    ↓

ai_interpretations.id = 55

```


This allows:


- debugging;

- replay;

- source inspection;

- AI traceability.

# 13. Idempotency and Unique Constraints


Collectors must be rerunnable.


### Daily price


```text

(instrument_id, trading_date, source_id)

```


### Institutional flow


```text

(instrument_id, source_id, trading_date, flow_type)

```


### Ownership


```text

(instrument_id, source_id, snapshot_date, holder_bucket)

```


### Estimate snapshots


The logical uniqueness depends on provider semantics.


Recommended:


```text

(instrument_id, source_id, metric, fiscal_period_label, observed_at)

```


If a provider only updates once per calendar day, normalize `observed_at` or introduce `snapshot_date`.


Do not generate duplicate snapshots simply because the same job retried five minutes later.


---


# 14. Snapshot Retention


MVP recommendation:


- keep all normalized snapshots;

- keep all changes;

- keep all job runs;

- keep raw payloads indefinitely while dataset remains small.


Later retention policy may:


- compress old raw payloads;

- delete low-value duplicated raw responses;

- move archived raw data to object storage.


Do not prematurely optimize retention.

# 15. Query Patterns


## What changed in the last 24 hours?


```sql

SELECT *

FROM changes

WHERE detected_at >= now() - interval '24 hours'

  AND total_score >= 50

ORDER BY total_score DESC, detected_at DESC;

```


---


## Important AMD changes


```sql

SELECT c.*

FROM changes c

JOIN instruments i ON i.id = c.instrument_id

WHERE i.symbol = 'AMD'

  AND i.market = 'US'

  AND c.total_score >= 70

ORDER BY c.detected_at DESC;

```

SELECT es.*

# 16. Index Strategy


Do not index every column.


MVP priorities:


### Time-series lookup


```text

instrument_id + date DESC

```


### Dashboard feed


```text

detected_at DESC + score

```


### Category filtering


```text

category + detected_at

```


### Raw inspection


```text

source_id + fetched_at

```


### Search


Start with normal B-tree indexes.


If instrument/company fuzzy search becomes important, add PostgreSQL `pg_trgm` later.


Do not introduce Elasticsearch for MVP search.

# 17. Partitioning


Do not partition tables in MVP.


Expected data volume for tens to hundreds of instruments with daily snapshots is small enough for normal PostgreSQL tables.


Only consider table partitioning after measured growth justifies it.


Likely future candidates:


- `raw_ingestions`

- `news_items`

- `price_daily`

- `changes`


---


# 18. Delete Behavior


Reference data:


```text

data_sources

instruments

```


should rarely be deleted.


Prefer:


```text

is_active = false

```


rather than destructive deletion.


Watchlist relationships may use cascading deletes.


Historical financial and change data should generally not cascade from an instrument deletion in production.


For MVP, avoid deleting instruments after data exists.


---


# 19. Schema Migration Rules


Use Alembic.


Rules:


1. Every schema change requires a migration.

2. Never manually mutate production schema.

3. Review autogenerated migrations.

4. Avoid destructive column drops in the same deployment that stops writing them.

5. Add → migrate data → switch application → remove later.

6. Seed `data_sources` separately from table migrations where practical.

# 23. Important Invariants


## Invariant 1


AI-generated values never overwrite deterministic fields.


## Invariant 2


A change must be traceable to its source snapshots.


## Invariant 3


Snapshots are historical records, not mutable current-state rows.


## Invariant 4


Provider retries are idempotent.


## Invariant 5


A raw ingestion may be re-normalized without calling the provider again.


## Invariant 6


Normalized financial values always have an explicit unit.


## Invariant 7


A market-native date is stored as a date, not inferred later from a UTC timestamp.
